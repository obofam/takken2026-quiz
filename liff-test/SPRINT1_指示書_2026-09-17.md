## 1. ゴール（これが動けば完了）

1. **PCの入口**：メールアドレスを入れると届くリンク（マジックリンク）でログインできる。パスワードなし。
2. **LINEの入口**：LIFF で開くと LINE ログインが通る（今の `api/session.js` の検証を流用）。
3. **同一人物の連結**：メールでログインした人が「LINEと連携」を押し、LIFF で一度開くと、メールと LINE が同じ利用者IDに結ばれる。逆順（LINEが先）でも結べる。
4. **記録を1行送る**：`ep10-preview.html` で1問答えるごとにサーバーへ1行保存。別端末でログインすると同じ記録が復元される。端末内保存（localStorage）は残し、オフライン時のキャッシュとして使う。
5. **試作中の制限**：ログインできるのは許可リスト（Kei と Kei が指定した数人）のみ。`api/session.js` の運営者ハッシュ限定を、許可リストのテーブル参照に置き換える。
6. 既存テスト（`npm test`・13件）が通り、新規の検証（セッション署名・回答の妥当性）が追加されている。

## 2. 構成（推奨。理由があれば変えてよいが、変えた理由を README に書く）

- **Vercel**（既存）＋ **Supabase**（Postgres と Auth）。自前サーバーは持たない。
- **クライアントは Supabase に直接つながない。** すべて `api/*` のサーバー関数経由。クライアントが持つのは httpOnly の署名付きセッションCookie だけ。
  - LINE：`api/session.js` で IDトークン検証 → 利用者IDを引く（無ければ作る）→ Cookie 発行。
  - メール：Supabase Auth のマジックリンクで届いたトークンをサーバーで検証（`auth.getUser`）→ 同じ形の Cookie 発行。
  - 連結：ログイン済みの状態でもう一方の入口を通ったら、その identity を同じ利用者IDに紐づける。
- **テーブル（最小）**
  - `users`（id, created_at）
  - `identities`（user_id, provider: 'line' | 'email', subject: LINEはsubのSHA256／メールは正規化したアドレス, unique(provider, subject)）
  - `allowlist`（provider, subject）… 試作中のみ
  - `attempts`（id, user_id, quiz_id 例 'ep10', started_at）
  - `answers`（id, attempt_id, user_id, quiz_id, question_id, value: true/false/null, answered_at）… 1問1行。集計は後で SQL
  - `entitlements`（user_id, plan: 'karte' | 'navi' | 'bansou', valid_until, source）… Sprint 3 用に空で用意
- **`ep10-preview.html` の変更範囲**：`PROGRESS_STORE_BEGIN〜END` と `KARTE_SUMMARY_BEGIN〜END` の中はテストが読むので原則不変。同期は外側に「回答後に `POST /api/answers`、読込時に `GET /api/answers?quiz=ep10` で復元」の層を足す。復元と端末内保存が食い違ったら、サーバー側を正とする。
- **環境変数名（例）**：`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SESSION_SECRET`, `LINE_CHANNEL_ID`。`.env.local` は `.gitignore` 済み。
