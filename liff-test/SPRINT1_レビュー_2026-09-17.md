## A. Astra が直すもの（優先順）

1. **LINE連携チケットが消える**（`ep10-preview.html:279`）：`hasPendingLink()` を `liff.init()` の前に評価している。LIFF経由では hash が `?liff.state=` に包まれ、`liff.init()` 後にしか戻らない。ログイン済みブラウザで連携URLを開くと早期 return でチケット未消費・無言。→ `liff.init()` と `captureLink()` を先に済ませてから判定する。
2. **旧 index.html が固まる**（`app.js:27`）：`liff.state` があると `ready=true` の前に return し、二度と有効化されない。LIFF は `history.replaceState` で同一実行内に解決するので、return せずに続行するか、解決後に再実行する。
3. **同期が永遠に pending**（`sync.js:36`）：401/403 以外（400 invalid_answer・409 history_limit・503）は行を残したまま `pending` に戻り、focus/online のたびに再送。→ 400/409 は「送れない行」として隔離（dead-letter）し `failed` 状態を出す。503 だけ再試行。
4. **内部エラーコードが画面に出る／`?auth=failed` を読んでいない**（`ep10-preview.html:293, 296`・`auth-callback.js:9`）：コード→日本語の対応表を1か所に置き（文言は Claude が下記 B で渡す）、`auth` クエリも読んで表示に流す。それまでは `e.message` を直接出さない。
5. **ローカル保存成功なのに「未保存」表示**（`ep10-preview.html:145`）：`progressStore.save()` と `enqueue()` を同じ try に入れている。分けて、enqueue 失敗は「端末には保存済み・サーバー送信待ち」に。あわせて `unsentAnswers` の二重キューは廃止し、`answer()` から直接 `enqueue()` でよい（`sync.js` 側の localStorage キューが正）。
6. **Origin ヘッダー厳密一致**（`lib/server.js:26`）：Origin を送らない WebView で全 POST が 403。`Sec-Fetch-Site: same-origin` か Referer の同一オリジンを代替として許可する（Cookie は SameSite=Lax なので CSRF 耐性は保てる）。
7. **例外がログに残らない**（`lib/server.js:72`）：`endpoint()` の catch で HttpError 以外は `console.error` に要約（トークン等は出さない）。
8. **plan コードが公開名**（`supabase/migrations/…sprint1.sql:53`）：`'karte','navi','bansou'` → 内部名 `'ume','take','matsu'` に。まだ未適用なので migration ファイルを直すだけでよい。
9. **無駄な往復**（`sync.js:62,70`・`ep10-preview.html:253-259, 278`）：POST ごとの `restore()` をやめてキューを空にしてから1回。focus/online/storage の `refresh()` は 2〜3秒のデバウンス。初期化時の `/api/session` 二重呼び出しを1回に。

### 実機一周の結果（Claude・2026-09-17 14:40）

デプロイ済み（`fbd21c6` を `vercel --prod`、`https://mimiobo-liff-test.vercel.app`）。PC の Chrome で確認：
- メール要求 → 既定テンプレのリンク → `auth-callback.html` → `POST /api/email-verify` **200** → 「ログイン中」→ 3問回答 → `POST /api/answers` 200 ×3 → 同期状態 `synced`「保存しました。」→ Supabase に users 1・answers 3 を REST で確認。**メール入口と1行保存は動いた。**
- 落ちたケース：Gmail の中からリンクを開くと `email-verify` が 401（Kei の1回目、Claude の1回目）。同じタブから検証URLを開いた場合は 200。Supabase 側は毎回 `Login` 成功。原因はブラウザ側の要求Cookie（`mimiobo_email_flow`）が届かない経路があること（Gmail アプリ／別ブラウザ／リダイレクタ経由）。
- 既定メールの送信上限（1時間に2通程度）に当たり `429 try_later` を確認。文言表に `try_later` を追加すること（下記 A-12）。

**A-12（Astra へ）：メール検証を要求Cookieに縛らない。** access_token（または token_hash）が本物で、そのメールが allowlist にあれば、要求Cookieが無くてもログインを許可する（トークン自体がメール所有の証明）。Cookie は連携チケット（`linkToken`）を運ぶ用途だけに残す。あわせて `ui-messages.js` に `try_later`：「メールの送信回数が上限に達しました。しばらくしてからもう一度お試しください。」を追加し、`/api/email` の 429 を画面に出す。テスト：Cookie なし＋有効トークン→200、Cookie なし＋allowlist 外→403。

### A-11 対応済み（Codex・2026-09-17）

- コールバックはtoken_hash／access_tokenの両経路に対応。fragment全体を通信前に消し、refresh_tokenは保存・送信しない。
